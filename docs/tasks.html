WORK & EVIDENCE

작업과 결과 확인

좋은 작업 지시는 원하는 결과와 확인 방법을 함께 담습니다. 큰 게임 기능은 작은 기능 단위로 나눠 맡겨 주세요.

완료 조건을 구체적으로

  • 어떤 파일이나 기능을 만들지
  • 입력과 출력은 무엇인지
  • 경계값이나 실패 조건은 무엇인지
  • 어떤 테스트를 통과해야 하는지

‘완료 조건 자세히 정하기’에서 필수 파일을 지정할 수 있습니다. 모델이 만들었다고 설명해도 실제 파일이 없으면 통과하지 않습니다.

고정 테스트

Python unittest 코드를 넣으면 작업 폴더와 분리해 저장합니다. 개발 에이전트의 파일 도구는 이 파일을 수정할 수 없습니다. 작업 폴더의 테스트와 고정 테스트를 모두 통과해야 합니다.

import unittest
from health import clamp_health

class Acceptance(unittest.TestCase):
    def test_limits(self):
        self.assertEqual(clamp_health(-5), 0)
        self.assertEqual(clamp_health(150), 100)

Python 테스트 코드는 별도 프로세스에서 현재 사용자 권한으로 실행됩니다. VM 보안 격리는 아니므로 신뢰하는 작업과 검증 코드만 사용하세요.

작업과 대화 읽기

작업을 열면 팀원별 설명을 시간순으로 볼 수 있습니다. ‘실행 근거 보기’는 모델 응답, 도구 호출, 테스트 로그까지 표시합니다. 팀원 필터로 특정 담당자의 기록을 볼 수도 있습니다.

실패와 수정

검증이 실패하면 개발 담당에게 결과를 전달합니다. 팀 설정의 자동 수정 한도까지 반복하고, 해결하지 못하면 ‘확인 필요’로 남깁니다. 모델의 성공 선언만으로 완료하지 않습니다.

결과물 받기

완료 또는 실패한 작업에서 보고서와 ZIP을 받을 수 있습니다. 보고서에는 확인 범위와 남은 문제가 포함됩니다. 파일 해시는 검증한 버전과 결과물이 같은지 확인하는 데 사용합니다.

현재 실제 실행 검증은 Python입니다. C#·C++ 파일은 생성할 수 있지만 해당 컴파일러와 엔진 검증을 통과했다고 간주하지 않습니다.

예전 작업과 긴 대화 찾기

작업과 대화 화면에서 이름이나 작업 ID를 검색하세요. 검색은 최근 목록에 없는 오래된 작업도 포함합니다. 상태 필터를 함께 적용하고, 이전·다음 버튼으로 30개씩 확인할 수 있습니다. 작업을 열면 최근 대화 200개를 표시하며, 이전 대화 불러오기로 남은 기록을 차례대로 볼 수 있습니다. 팀원 필터는 현재 불러온 대화에 적용되므로 이전 대화도 불러온 뒤 확인하세요.

대화 내보내기

작업 상세에서 대화 JSON 내보내기를 누르면 현재 선택한 담당자의 전체 기록을 저장합니다. 모든 팀원을 선택하면 작업 전체 대화를 내보냅니다. 이전 대화를 화면에 모두 불러올 필요는 없습니다. 최대 5만 개 기록을 내보내며, 더 많으면 담당자별로 나누세요. 작업에 적은 개인정보도 포함될 수 있으므로 공유 전에 확인하세요.

등록 응답이 끊겼을 때

서버가 작업을 등록한 뒤 응답만 유실될 수 있습니다. 같은 화면에서 내용을 바꾸지 않고 다시 제출하면 동일 요청 ID를 사용해 중복 등록을 막습니다. 창을 새로 열거나 새로 고쳤다면 최근 작업을 먼저 확인하세요.

취소 후 응답

이미 진행 중인 모델 호출이나 파일 쓰기는 바로 멈추지 않을 수 있습니다. 취소를 확인한 뒤 돌아온 단계 응답은 다음 담당자에게 전달하지 않으며 완료 처리하지 않습니다.

누가 수행하고 누구에게 전달했는지

새 기록에는 수행 팀원·실행 역할·수신 팀원을 저장합니다. 한 팀원이 여러 역할을 맡아도 대화 머리글의 ‘개발·검증’ 표시로 단계를 구분합니다. 팀원 필터와 JSON 내보내기는 그 팀원이 보낸 기록, 받은 지시·인계, 작업의 최초 지시를 포함합니다. 당시 저장한 팀 구성과 이름을 사용하므로 현재 팀 설정을 바꾸어도 과거 담당자가 바뀌지 않습니다. 기록 분리는 권한·OS 보안 격리가 아닙니다.

추가 지시는 선택한 팀원의 다음 모델 요청에 포함됩니다. 이미 실행 중인 요청을 변경하지 않습니다. 필수 파일을 바로 생성하는 경로와 별도 Ollama 경로에도 같은 수신 구분을 적용합니다. 역할 이름으로 API에 지시하면 그 작업에 배정된 팀원에게 전달하고 해당 역할의 실행에 적용합니다. 실제 팀원 ID와 역할 이름이 같으면 팀원 ID를 우선합니다. 실행하지 않는 역할은 거절합니다.

완료 시 저장한 agents/<팀원 ID>/messages.json과 보고서는 그 시점의 스냅샷입니다. 완료 후 추가한 메모까지 받으려면 화면의 대화 JSON 내보내기를 사용하세요. 기존 기록의 수신자는 저장된 JSON·전달 문자열에서 읽을 수 있는 경우에만 보완하며, 기록에 없는 실행 역할을 추정해서 채우지 않습니다.

추가 지시의 수신 목록에는 그 작업에 배정된 팀원만 표시합니다. 팀에 있어도 이번 작업에 배정되지 않은 팀원에게 실행 지시를 보내면 거절합니다. 팀 구성 기록이 없는 초기 버전의 작업은 서버와 같은 기본 4역할 호환 구성으로 표시합니다.

수정이 반복될 때의 지시 맥락

모델에 전달하는 최근 인계는 최대 6개입니다. 해당 팀원·역할에 보낸 최근 사용자 지시를 최대 3개까지 우선 유지하고 나머지를 최근 담당자 인계로 채웁니다. 개발·검증 인계가 반복되어도 이 사용자 지시가 그 인계들 때문에 밀려나지 않습니다. 더 오래된 추가 지시는 전체 대화에 보존되지만 모델 맥락에서 빠질 수 있습니다. 변하면 안 되는 요구사항은 최초 작업 내용·고정 검증 코드에도 명시하세요.

보고서를 읽는 방법

MD 보고서는 담당자 이름·실행 역할·전달 대상과 결과 요약을 먼저 보여줍니다. 테스트 0개인 파일 검토와 데모 흐름 확인을 실제 실행 테스트 통과로 표시하지 않습니다. 파일이 검증 후 바뀌면 현재 파일의 재검증이 필요하다고 표시하며 과거 검사 결과는 JSON에 보존합니다. 전체 모델 응답·대화·검증 로그는 report.json에 있습니다. 보고서 ID로 MD·JSON·ZIP이 같은 스냅샷인지 확인할 수 있습니다.

결과 파일을 임시 영역으로 복사하고 해시를 대조한 뒤 보고서·ZIP을 만듭니다. ZIP 생성 중 실패하면 이전 보고서를 보존합니다. 각 파일은 완성된 파일로 교체하며 파일 여러 개의 교체가 하나의 OS 트랜잭션인 것은 아닙니다. ZIP 안의 보고서와 결과 파일은 같은 스냅샷이고, 묶음에는 팀원별 대화 JSON도 포함합니다. 링크·작업 폴더 밖 파일은 결과물과 체크포인트에 포함하지 않습니다.

이 형식은 새로 생성하는 보고서부터 적용됩니다. 이전 보고서와 검증 근거를 자동으로 다시 작성하지 않습니다. 보고서의 자동 검사 결과와 담당자 판단은 서로 구분해서 읽어 주세요.

결과 파일이 보이지 않을 때

작업 상세는 안전하게 열 수 있는 파일만 다운로드 링크로 표시합니다. 파일이 없으면 기록·저장소 확인을 안내하고 조회 실패 시 다시 확인할 수 있습니다. JSON만 남으면 검증 기록 JSON을 제공합니다. 실행 근거 보기에서는 JSON 링크도 표시합니다. 이 목록은 존재·읽기 가능 여부이며 검증 성공 판정이 아닙니다.

파일은 64KB씩 읽어 전송하며 ZIP 전체를 서버 메모리에 올리지 않습니다. 다운로드 이름에는 작업 ID를 포함합니다. 폴더 밖 경로와 심볼릭 링크·정션·하드링크는 제공하지 않습니다. HEAD는 결과 파일 정보만 조회하며 화면 캡처 등 다른 API에는 연결하지 않습니다.
