작업과 결과 확인

대화에서 담당자를 구분하고 결과를 확인하세요.

  1. 최근 작업 또는 작업과 대화에서 작업을 여세요.
  2. 팀원별 대화와 검증 결과를 확인하세요.
  3. 완료하면 결과물 받기 또는 보고서를 여세요.
완료 조건·추가 지시·복구

좋은 작업 지시는 원하는 결과와 확인 방법을 함께 담습니다. 큰 게임 기능은 작은 기능 단위로 나눠 맡겨 주세요.

완료 조건을 구체적으로

  • 어떤 파일이나 기능을 만들지
  • 입력과 출력은 무엇인지
  • 경계값이나 실패 조건은 무엇인지
  • 어떤 테스트를 통과해야 하는지

‘실행 설정과 완료 조건’에서 필수 파일을 지정할 수 있습니다. 작업 폴더 안의 상대 경로를 사용하며 상위 폴더 이동·예약 파일명은 접수하지 않습니다. 모델이 만들었다고 설명해도 실제 파일이 없으면 통과하지 않습니다.

고정 테스트

Python unittest 코드를 넣으면 작업 폴더와 분리해 저장합니다. 개발 에이전트의 파일 도구는 이 파일을 수정할 수 없습니다. 작업 폴더의 테스트와 고정 테스트를 모두 통과해야 합니다.

import unittest
from health import clamp_health

class Acceptance(unittest.TestCase):
    def test_limits(self):
        self.assertEqual(clamp_health(-5), 0)
        self.assertEqual(clamp_health(150), 100)

Python 테스트 코드는 별도 프로세스에서 현재 사용자 권한으로 실행됩니다. VM 보안 격리는 아니므로 신뢰하는 작업과 검증 코드만 사용하세요.

작업과 대화 읽기

작업을 열면 팀원별 설명을 시간순으로 볼 수 있습니다. ‘실행 근거 보기’는 모델 응답, 도구 호출, 테스트 로그까지 표시합니다. 팀원 필터로 특정 담당자의 기록을 볼 수도 있습니다.

실패와 수정

검증이 실패하면 개발 담당에게 결과를 전달합니다. 팀 설정의 자동 수정 한도까지 반복하고, 해결하지 못하면 ‘확인 필요’로 남깁니다. 모델의 성공 선언만으로 완료하지 않습니다.

결과물 받기

완료 또는 실패한 작업에서 보고서와 ZIP을 받을 수 있습니다. 보고서에는 확인 범위와 남은 문제가 포함됩니다. 파일 해시는 검증한 버전과 결과물이 같은지 확인하는 데 사용합니다.

현재 실제 실행 검증은 Python입니다. C#·C++ 파일은 생성할 수 있지만 해당 컴파일러와 엔진 검증을 통과했다고 간주하지 않습니다.

예전 작업과 긴 대화 찾기

작업과 대화 화면에서 이름이나 작업 ID를 검색하세요. 검색은 최근 목록에 없는 오래된 작업도 포함합니다. 상태 필터를 함께 적용하고, 이전·다음 버튼으로 30개씩 확인할 수 있습니다. 작업을 열면 최근 대화 200개를 표시하며, 이전 대화 불러오기로 남은 기록을 차례대로 볼 수 있습니다. 팀원 필터는 현재 불러온 대화에 적용되므로 이전 대화도 불러온 뒤 확인하세요.

대화 내보내기

작업 상세에서 대화 JSON 내보내기를 누르면 현재 선택한 담당자의 전체 기록을 저장합니다. 모든 팀원을 선택하면 작업 전체 대화를 내보냅니다. 이전 대화를 화면에 모두 불러올 필요는 없습니다. 최대 5만 개 기록을 내보내며, 더 많으면 담당자별로 나누세요. 작업에 적은 개인정보도 포함될 수 있으므로 공유 전에 확인하세요.

등록 응답이 끊겼을 때

서버가 작업을 등록한 뒤 응답만 유실될 수 있습니다. 같은 화면에서 내용을 바꾸지 않고 다시 제출하면 동일 요청 ID를 사용해 중복 등록을 막습니다. 창을 새로 열거나 새로 고쳤다면 최근 작업을 먼저 확인하세요.

취소 후 응답

이미 진행 중인 모델 호출이나 파일 쓰기는 바로 멈추지 않을 수 있습니다. 취소를 확인한 뒤 돌아온 단계 응답은 다음 담당자에게 전달하지 않으며 완료 처리하지 않습니다.

누가 수행하고 누구에게 전달했는지

새 기록에는 수행 팀원·실행 역할·수신 팀원을 저장합니다. 한 팀원이 여러 역할을 맡아도 대화 머리글의 ‘개발·검증’ 표시로 단계를 구분합니다. 팀원 필터와 JSON 내보내기는 그 팀원이 보낸 기록, 받은 지시·인계, 작업의 최초 지시를 포함합니다. 당시 저장한 팀 구성과 이름을 사용하므로 현재 팀 설정을 바꾸어도 과거 담당자가 바뀌지 않습니다. 기록 분리는 권한·OS 보안 격리가 아닙니다.

추가 지시는 선택한 팀원의 다음 모델 요청에 포함됩니다. 이미 실행 중인 요청을 변경하지 않습니다. 필수 파일을 바로 생성하는 경로와 별도 Ollama 경로에도 같은 수신 구분을 적용합니다. 역할 이름으로 API에 지시하면 그 작업에 배정된 팀원에게 전달하고 해당 역할의 실행에 적용합니다. 실제 팀원 ID와 역할 이름이 같으면 팀원 ID를 우선합니다. 실행하지 않는 역할은 거절합니다.

완료 시 저장한 agents/<팀원 ID>/messages.json과 보고서는 그 시점의 스냅샷입니다. 완료 후 추가한 메모까지 받으려면 화면의 대화 JSON 내보내기를 사용하세요. 기존 기록의 수신자는 저장된 JSON·전달 문자열에서 읽을 수 있는 경우에만 보완하며, 기록에 없는 실행 역할을 추정해서 채우지 않습니다.

추가 지시의 수신 목록에는 그 작업에 배정된 팀원만 표시합니다. 팀에 있어도 이번 작업에 배정되지 않은 팀원에게 실행 지시를 보내면 거절합니다. 팀 구성 기록이 없는 초기 버전의 작업은 서버와 같은 기본 4역할 호환 구성으로 표시합니다.

수정이 반복될 때의 지시 맥락

모델에 전달하는 최근 인계는 최대 6개입니다. 해당 팀원·역할에 보낸 최근 사용자 지시를 최대 3개까지 우선 유지하고 나머지를 최근 담당자 인계로 채웁니다. 개발·검증 인계가 반복되어도 이 사용자 지시가 그 인계들 때문에 밀려나지 않습니다. 더 오래된 추가 지시는 전체 대화에 보존되지만 모델 맥락에서 빠질 수 있습니다. 변하면 안 되는 요구사항은 최초 작업 내용·고정 검증 코드에도 명시하세요.

보고서를 읽는 방법

MD 보고서는 담당자 이름·실행 역할·전달 대상과 결과 요약을 먼저 보여줍니다. 테스트 0개인 파일 검토와 데모 흐름 확인을 실제 실행 테스트 통과로 표시하지 않습니다. 파일이 검증 후 바뀌면 현재 파일의 재검증이 필요하다고 표시하며 과거 검사 결과는 JSON에 보존합니다. 전체 모델 응답·대화·검증 로그는 report.json에 있습니다. 보고서 ID로 MD·JSON·ZIP이 같은 스냅샷인지 확인할 수 있습니다.

결과 파일을 임시 영역으로 복사하고 해시를 대조한 뒤 보고서·ZIP을 만듭니다. ZIP 생성 중 실패하면 이전 보고서를 보존합니다. 각 파일은 완성된 파일로 교체하며 파일 여러 개의 교체가 하나의 OS 트랜잭션인 것은 아닙니다. ZIP 안의 보고서와 결과 파일은 같은 스냅샷이고, 묶음에는 팀원별 대화 JSON도 포함합니다. 링크·작업 폴더 밖 파일은 결과물과 체크포인트에 포함하지 않습니다.

이 형식은 새로 생성하는 보고서부터 적용됩니다. 이전 보고서와 검증 근거를 자동으로 다시 작성하지 않습니다. 보고서의 자동 검사 결과와 담당자 판단은 서로 구분해서 읽어 주세요.

결과 파일이 보이지 않을 때

작업 상세는 안전하게 열 수 있는 파일만 다운로드 링크로 표시합니다. 파일이 없으면 기록·저장소 확인을 안내하고 조회 실패 시 다시 확인할 수 있습니다. JSON만 남으면 검증 기록 JSON을 제공합니다. 실행 근거 보기에서는 JSON 링크도 표시합니다. 이 목록은 존재·읽기 가능 여부이며 검증 성공 판정이 아닙니다.

파일은 64KB씩 읽어 전송하며 ZIP 전체를 서버 메모리에 올리지 않습니다. 다운로드 이름에는 작업 ID를 포함합니다. 폴더 밖 경로와 심볼릭 링크·정션·하드링크는 제공하지 않습니다. HEAD는 결과 파일 정보만 조회하며 화면 캡처 등 다른 API에는 연결하지 않습니다.

추가 지시를 보낸 뒤 응답이 끊겼을 때

같은 화면에서 내용과 수신자를 바꾸지 않고 다시 보내면 같은 요청 ID로 확인합니다. 이미 접수됐다면 대화·전달 큐를 중복 생성하지 않습니다. 서버는 요청 ID를 작업 기록과 함께 보존하지만 브라우저의 재전송 ID는 현재 페이지에만 남습니다. 새로고침·다른 내용 전송 후에는 기존 대화를 먼저 확인하세요. 전송 응답을 기다리는 동안 새로 작성한 입력은 이전 응답이 도착해도 지우지 않습니다.

작업 등록과 최초 지시, 취소·재개·일시 중지 상태와 제어 기록은 각각 한 번에 저장합니다. 기록 저장이 실패하면 해당 상태 변경도 적용하지 않습니다. 저장소 오류가 나면 폴더 권한·디스크 상태를 확인한 뒤 다시 시도하세요. 제어 기록은 요청을 저장했다는 뜻이며 이미 진행 중인 모델 요청이나 전달된 VM 입력이 즉시 중단됐다는 뜻은 아닙니다.

Python 검증이 멈추거나 로그가 많을 때

각 Python 검증은 기본 30초 제한을 적용합니다. 시간 초과는 검증 실패로 기록하며 해당 검증 프로세스를 정리합니다. 수정 횟수에 여유가 있으면 수정 단계로 돌아가고, 한도를 넘으면 실패로 보존한 뒤 다음 대기 작업을 처리합니다.

Windows에서는 작업 코드를 읽기 전에 검증 전용 Job Object에 연결합니다. 검증이 끝나면 정상 종료 여부와 관계없이 그 검증이 만든 하위 프로세스도 종료합니다. 테스트가 띄운 백그라운드 서버를 계속 유지하는 용도로 사용할 수 없습니다. 이 묶음을 준비하지 못하면 작업 코드를 실행하지 않고 검증 실패로 표시합니다.

Python 출력은 마지막 20,000자, 직접 출력의 파이프는 stdout·stderr별 마지막 32KiB를 보관합니다. 기록이 잘리면 JSON 검증 결과의 output_truncated 또는 native_output_truncated에 표시합니다. 이는 출력 수집량 제한입니다. 테스트 코드 자체의 메모리·디스크·네트워크 사용을 제한하는 보안 샌드박스는 아니며 호스트 사용자 권한으로 실행됩니다.

작업을 오가며 지시 작성하기

작성 중인 추가 지시와 수신 팀원은 작업별로 현재 페이지 안에 보관합니다. 다른 작업을 열면 그 작업의 초안이나 빈 입력란을 표시하며, 이전 작업으로 돌아오면 작성하던 내용을 복원합니다. 응답을 기다리는 중 작업을 바꾸어도 다른 작업의 초안을 지우지 않습니다. 응답이 끊긴 작업으로 돌아와 내용과 수신자를 바꾸지 않고 다시 보내면 같은 요청 ID를 사용합니다.

초안은 전달하기 전까지 서버에 저장하지 않으며 페이지를 새로고침하거나 닫으면 사라집니다. 미전송 작업 제목·필수 파일·고정 검증·VM 동작·추가 지시가 남아 있으면 브라우저의 이탈 확인을 요청합니다. 새 작업 접수 응답을 기다리는 동안 다음 작업을 작성하면 새 입력을 보존하며 기존 작업 창을 자동으로 열어 방해하지 않습니다.

설명만 입력하고 시작하기

입력란 위의 현재 모드·환경을 확인하고 작업을 설명한 뒤 팀에 맡기세요. 첫 모드는 서버의 기본 설정을 따르며 선택한 값은 자동 갱신으로 덮어쓰지 않습니다. 별도 파일·고정 검증·VM 동작이 필요할 때만 실행 설정과 완료 조건을 여세요. 접어도 입력은 유지되며 추가 조건의 종류와 파일 수가 표시됩니다.

접수한 작업과 다음 초안 구분

작업 접수 응답을 확인하고 대기 중 입력이 바뀌지 않았으면 제목과 그 작업의 파일·고정 검증·VM 동작 조건을 함께 비웁니다. 실행 모드와 환경 선택은 유지합니다. 접수 실패나 응답 유실 때는 내용을 남기며, 그대로 다시 보내면 같은 요청 ID를 사용합니다. 응답 대기 중 편집한 내용은 JSON 공백 편집도 포함해 보존합니다. 제목 없이 고급 조건만 작성했거나 VM 동작 JSON이 아직 미완성이어도 페이지 이탈 확인을 요청합니다. 브라우저가 이탈 확인을 표시하는지는 사용자 상호작용과 브라우저 정책에 따라 달라지며, 초안을 자동 저장하는 기능은 아닙니다.

접수는 됐는데 화면을 불러오지 못한 경우

접수 응답을 확인하면 작업 ID와 작업 확인 링크를 남깁니다. 이후 화면 갱신이나 상세 조회가 실패해도 접수 실패로 표시하지 않습니다. 다시 등록하는 대신 작업 확인을 눌러 해당 ID로 검색하세요. 조회가 복구되면 작업 목록에서 대화를 다시 열 수 있습니다. 확인 줄은 현재 페이지의 최근 접수에 대한 것이며 새로고침 후에는 작업과 대화에서 찾으세요. 접수 응답 자체를 받지 못한 경우에는 기존 입력을 유지하고 같은 요청으로 재시도합니다.

취소와 중단 경계

일시 중지나 앱 종료를 위해 현재 작업을 대기로 돌리는 시점에 취소가 겹쳐도 취소 상태를 유지합니다. 이미 시작한 모델 호출을 즉시 중단한다는 의미는 아니며, 취소 후 응답은 다음 담당자에게 전달하지 않습니다.

저장된 실행 계획을 확인하지 못할 때

담당자·역할·실행 순서·환경·현재 단계가 손상된 작업은 모델이나 VM을 호출하기 전에 보류하고 다음 정상 대기 작업을 처리합니다. 손상된 계획을 재시도로 다시 실행하지 않습니다. 원래 요청과 기록을 확인해 새 작업으로 등록하세요. 작업 폴더 준비 실패는 실패로 기록하고 다음 작업으로 넘어갑니다. 파일 시스템 오류로 보고서까지 저장하지 못한 경우에는 작업 상태와 오류 기록도 함께 확인하세요.

추가 지시가 반영되는 시점

진행 중인 작업의 담당자를 선택해 지시를 보내세요. 아직 읽지 않은 지시는 해당 단계의 맥락에 포함합니다. 단계 실행 중이나 이미 지난 담당자에게 도착하면 기존 응답을 다음 단계로 넘기지 않고 담당 단계부터 새 지시를 포함해 다시 처리합니다. 안내의 기록됨은 모델이 지시를 지켰다는 검증을 뜻하지 않습니다.

실패·중단된 작업에는 지시를 저장한 뒤 다시 이어가기를 누르세요. 완료·취소된 작업의 새 지시는 적용하지 않고 입력을 유지합니다. 새 작업으로 맡겨 주세요. 응답이 유실돼 같은 지시를 다시 보내면 같은 요청 기록을 확인하며 중복 재실행하지 않습니다.

돌아갈 구간에 VM 키·마우스 입력이 있으면 자동 반복하지 않고 보류합니다. 게스트 상태를 확인한 뒤 수동으로 재개하세요. 이미 실행한 파일 쓰기나 입력은 되돌리지 않습니다. 대화 전체는 보존하지만 모델에는 기존처럼 최근 지시 최대 3개를 우선 전달합니다.

지시 저장 후 화면 갱신이 실패한 경우

서버의 저장 응답을 받으면 최근 지시 저장 완료를 표시합니다. 이후 대화·상태 조회만 실패해도 지시를 다시 보내지 마세요. 기록 다시 조회는 저장된 최근 대화만 읽으며 지시를 재전송하지 않습니다. 이전 대화는 다시 불러올 수 있습니다.

현재 입력은 별도 미전송·전송 확인 중·전송 결과 미확인으로 구분합니다. 새로 작성한 초안은 이전 지시의 저장 응답으로 지우지 않습니다. 확인 표시는 작업별로 이 페이지에서만 유지되며 실제 지시 기록은 서버에 남습니다. 새로고침 후에는 대화에서 기록을 확인하세요. 저장됨 표시는 모델의 지시 준수를 검증한 결과가 아닙니다.
